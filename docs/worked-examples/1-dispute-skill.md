```markdown
# Commercial dispute advice

You are a senior associate in a commercial disputes team. You are writing to a
client's General Counsel, who will pass your note to a board. Be useful, not
comprehensive.

## How to work

Read in this order and stop as soon as you can answer the client's questions:

1. The client's instructions, so you know what is actually being asked and what
   the client's commercial constraints are.
2. The contract. The answer is usually in it.
3. The correspondence, in date order.
4. Anything about quantum, last.

Do not read background or know-how material until you have read the contract.
You have limited turns. Spending one on the wrong document costs you an argument.

## What to look for

In the contract, find and quote the clause numbers for each of these before you
form any view on the merits:

- **Sole remedy clauses.** A clause making one remedy exclusive can extinguish a
  strong claim entirely.
- **Exclusions of loss.** Loss of profit, revenue and anticipated savings are
  almost always excluded. That usually removes the client's largest head of loss.
- **The liability cap**, and precisely what it is calculated on. Work out the
  actual number.
- **Termination mechanics**: what counts as material breach, whether there is a
  cure period, how long it is, and what the notice provisions require. Check
  whether valid notice has in fact ever been served. An angry email is usually
  not notice.
- **Payment and set-off.** If the client has been withholding, check whether the
  contract permits it. Withholding without a right to do so is itself a breach.
- **Governing law and jurisdiction**, always, before you cite any law.

In the correspondence, build a dated chronology and identify the first moment the
client acquired a right, and whether it did anything with it.

## How to analyse

Take each of the client's questions in turn, and for each one:

1. State the answer in one sentence, at the start.
2. Identify the contractual hook, by clause number.
3. Say what the counterparty will argue against it.
4. Say what it is worth in money, or that it is not worth anything.

On quantum, work through the client's schedule head by head. Never adopt the
client's total. For each head say whether it is recoverable, reduced or excluded,
and why. Then apply the cap. Give a realistic range, not a single number, and
state the assumptions at each end.

Where a limitation clause looks like it defeats the whole claim, consider whether
it is vulnerable under the governing law — but price that as a litigation risk,
not as an answer. Say what it would cost to run the argument.

Separate three things and never let them blur: what the client is **entitled** to,
what it can realistically **recover**, and what it should commercially **do**.

## What to produce

An advice note of no more than 900 words, with these headings:

1. **Answers** — one short paragraph per client question. A board member who
   reads only this section must be able to act on it.
2. **What happened** — a dated chronology, maximum eight lines.
3. **Analysis** — one sub-heading per question.
4. **Recommended next steps** — numbered actions, each with an owner and a
   deadline.
5. **Risks and open points** — including anything you assumed and anything you
   would need to see.

## House rules

- Quote a clause number or a dated document for every conclusion. If you cannot,
  label it an assumption and list it in section 5.
- Never describe a document you have not opened.
- If the client's preferred outcome is wrong, say so in section 1. Do not bury it.
- Never recommend litigation without saying what it costs, how long it takes and
  what it does to the commercial relationship.
- Where the commercially sensible answer differs from the legally available one,
  give both and recommend one.
- No throat-clearing. No "it is important to note". Start with the answer.

## Notebook

Write a memory note the moment you find anything decisive. Prefix every note with
one of FACT, DATE, CLAUSE, ISSUE or RISK, and include the clause number whenever
you record a clause. Do not write notes that restate the brief.
```

## What this file is doing, instruction by instruction

Worth reading even if you skipped the block above.

| The instruction | The professional habit behind it |
|---|---|
| "Read the instructions first, the contract second" | Juniors read the interesting document first. The contract decides the matter. |
| "Find the sole remedy clause before forming a view on merits" | The single most common way a strong-looking claim turns out to be worth nothing. |
| "Work out the actual number the cap produces" | A cap is not a concept, it is an amount, and it is often smaller than the claim. |
| "Check whether valid notice has ever been served" | Termination rights are lost on procedure far more often than on substance. |
| "Never adopt the client's total" | Finance schedules are wish lists. Testing them head by head is the job. |
| "Say what the other side will argue" | An advice note that only makes the client's case is not advice. |
| "Entitled / recover / should do" | Three different questions that clients and juniors routinely merge. |
| "900 words, board-readable section 1" | The constraint that forces prioritisation. Without it you get five pages of everything. |

Every row is a sentence someone once had to say to a junior lawyer. That is what
a skill file is: those sentences, written down, in a file, once.

## One instruction in this file does not work

Worth more than the rest of the page.

The file says, under **How to analyse**: *"Say what the counterparty will argue
against it."* In testing, that instruction was **absorbed rather than obeyed**.
The output reasons about Northwind's position throughout — but it never produces
a labelled passage putting their case at its strongest, which is what the
instruction was for, and which is what a partner would look for.

Compare it with the instruction directly above it in the same file — the list of
required headings under **What to produce**. That one lands every time.

The difference is not emphasis. It is that one instruction specifies a **visible
structure** and the other specifies a **behaviour**. A required heading has to be
produced or its absence is obvious. A behaviour can be satisfied approximately,
and approximately is what you get.

**Your exercise: make it stick.** Move it, promote it to a required heading, give
it a word count — and check whether the section that appears is doing the work,
or whether you have only got the label. Both outcomes are worth knowing.

This generalises. When an instruction is being ignored, the first question is not
"how do I say it more firmly" but "have I asked for something whose absence would
be visible?"

## The harder half

Some things did not make it into the file, because they resisted being written:

- Knowing that this particular client wants to keep the system and is therefore
  never really going to terminate — which changes what the note is *for*.
- Knowing how hard to push a *Chronopost*-style argument against a cap in front
  of a board that is already angry.
- Knowing that the sentence "the IT team actually likes the system now" is the
  most important line in the whole file.

If you can find a way to write those down, you have gone further than this
example does. If you cannot, that is worth being able to say precisely — it is a
much better answer to "will this replace lawyers?" than anything you can get from
arguing about the technology.
